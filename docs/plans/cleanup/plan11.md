## Why this plan exists

Nothing here is search code; all of it is duplication that has already
mislead a reader or can silently drift:

1. **The validation field list duplicates the struct.** A 29-line array
   (27 name/value pairs) that a macro can generate from the field names
   alone.
2. **Three copies of the default scorer weights** with a claim ("match the
   compiled-in defaults") that no test enforces — a drift here changes
   move ordering silently and is *not* caught by the quick suite, because
   the quick suite's expectations were themselves derived from the same
   defaults.
3. **Two copies of the benchmark-fixture parser** (~55 lines) that must be
   edited together whenever a fixture gains a field.
4. **Four copies of the proofdb win-in-1 tree fixture** (~25 lines each).
5. **One dead 300-line measurement harness** whose verdict strings
   ("NO-GO (amplification): median fill ratio exceeds 50%") are code for a
   question that is closed.

## Normative design

### Phase A — validation list from field names

```rust
/// Expand `$($field),*` into `[(stringify!($field), $self.$field), …]`.
macro_rules! field_values {
    ($this:ident => $($field:ident),* $(,)?) => {
        [$((stringify!($field), $this.$field)),*]
    };
}

impl ScorerParams {
    pub fn validate(&self) -> Result<(), ScorerParamsError> {
        // 1. Non-negativity for all score-related fields.
        let non_negative = [
            field_values!(self => score_winning_capture, score_promotion, /* … all 21 … */),
            field_values!(self.pieces => pawn, knight, bishop, rook, queen, commoner),
        ]
        .concat();
        for (field, value) in non_negative { … }
```

Details the implementer must honour:

- A-1. The error payload keeps `field: &'static str` — `stringify!`
  produces `&'static str`, and for the piece fields the emitted name is
  bare (`pawn`, not `pieces.pawn`). **Preserve the current spelling** by
  giving the piece macro its own prefix:
  `concat!("pieces.", stringify!($field))` — the existing messages say
  `pieces.commoner must be non-negative`, and
  `tests/test_config.rs`/`params.rs` tests may assert on the message (check
  before changing; if nothing asserts it, a bare name is acceptable and
  simpler — decide once and record it).
- A-2. The array must remain `[(&'static str, i32)]` (no `Vec`, no
  allocation beyond the `concat()` of two const-sized arrays, which is
  one small `Vec` — acceptable; if the `Vec` is objectionable, write two
  loops instead of `concat()`, which is equivalent and allocation-free).
- A-3. Checks 2–5 (percent range, piece hierarchy, two score hierarchies)
  are **unchanged verbatim**; only check 1's input construction changes.
- A-4. `macro_rules!` is module-local, not exported (`macro_rules!` without
  `#[macro_export]`; place it directly above `impl ScorerParams`).
- A-5. The field list order matches the struct's declaration order (it
  does today); the macro cannot enforce that, so keep a one-line comment
  "keep in struct order".

### Phase B — `config.toml` drift test

Add to `src/config.rs`'s test module (which can reach the manifest dir):

```rust
/// The committed `config.toml` must equal the compiled-in defaults: its header
/// claims it, and a drifted copy silently changes every `--config` run.
#[test]
fn repo_config_toml_matches_defaults() {
    let path = std::path::Path::new(env!("CARGO_MANIFEST_DIR")).join("config.toml");
    let params = load_scorer_config(&path).expect("config.toml must load");
    assert_eq!(params, ScorerParams::default());
}
```

- B-1. This requires `ScorerParams`/`PieceValues` to implement
  `PartialEq` (they derive `Clone, Debug, Deserialize` today). Add
  `PartialEq` to both derives — a test-only need, no behaviour change, no
  serialization change.
- B-2. If `config.toml` is *already* drifted, the test fails on the first
  run: that is a **finding** — fix `config.toml` to match the defaults
  (the defaults are authoritative) and record the drift in the report.
- B-3. Do not delete `src/config.rs`'s `DEFAULT_TOML` fixture in the same
  session: it is a *deliberately independent* TOML (different numbers, used
  to prove that non-default values load and validate). Note in the report
  that its duplication is intentional.

### Phase C — one fixture parser

- C-1. Create `tests/common/fixture_parse.rs` containing the fixture
  parser *only* (`struct MoveOrderCase`, `parse_move_order_fixture`,
  `load_move_order_suite`, `load_decisive_suite`, and — added — the
  `MOVE_ORDER_FIXTURE`/`DECISIVE_FIXTURE` `include_str!`s with paths
  relative to `tests/common/`, i.e. `include_str!("../fixtures/…")`).
- C-2. `tests/common/mod.rs` becomes `pub mod fixture_parse; pub use
  fixture_parse::*;` plus its test-only helpers, so every existing
  `common::load_*` call site is untouched.
- C-3. `examples/common.rs` includes the same file:

```rust
#[path = "../tests/common/fixture_parse.rs"]
mod fixture_parse;
pub use fixture_parse::*;
```

  Verify the two things that can break: (a) the `include_str!` paths
  resolve relative to the *file containing the macro*, i.e.
  `tests/common/fixture_parse.rs` → `../fixtures/…` is
  `tests/fixtures/…` — correct for both users; (b) `#![allow(dead_code)]`
  at the top of `examples/common.rs` still covers the module (it is an
  inner attribute on the crate root of `common.rs`… it is a *module* file —
  confirm the allow applies, otherwise add `#[allow(dead_code)]` on the
  `mod` declaration).
- C-4. `examples/benchmark.rs:354` uses `common::M19_FEN.to_string()`
  instead of the literal. `tests/stress.rs:36` keeps its literal (it
  cannot include `examples/common.rs`); instead add one line to that
  test's doc comment naming `examples/common.rs` as the canonical source,
  and record the residual duplication in the report (2 copies, not 3).
- C-5. No fixture file changes; no fixture field changes.

- D-3. `tests/proofdb_merge_cli.rs` and `tests/proofdb_harvest_cli.rs`
